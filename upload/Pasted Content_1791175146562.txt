THE PRODUCT IN ONE PARAGRAPH
A digital business card that lives only on the user's phone. The user creates their card; the app generates a QR code that contains the contact itself (a compact vCard). Anyone scans it with the stock phone camera and gets "Add contact": no app, no web page, no server, no network. The QR can be beautified after generation, in the spirit of the profile-QR screens in Instagram and Telegram (presets, shapes, colours, centre avatar, backgrounds, fonts), while a plain QR is always one tap away. The user can show it fullscreen, share/export it (PNG, SVG, print-ready card, story image, .vcf file), save it to Google Wallet / Apple Wallet through a Wallet-optimised image, and turn it into a lock-screen wallpaper (applied directly on Android, saved plus guided on iOS). Everything is local, offline-first and privacy-first. It ships as a PWA and as Android/iOS apps through Capacitor.
Brand promise (must be true and verifiable): nothing leaves the phone. No accounts, no servers, no analytics, no tracking, no cloud backup, no third-party requests.
Non-goals: any backend or database server, authentication, public profile URLs, deep links, cloud sync, analytics or scan counts, in-app QR scanner, multiple cards, social login, push notifications, official Google Wallet API issuance (it needs a secret signing key and a server, which breaks the privacy model; mention it in the README as a deliberately excluded future option).

STAGE 4 - DESIGN SYSTEM FIRST (before building screens)
Design direction: Apple-level polish + editorial typography + cinematic restraint. Designed, not decorated. It should feel expensive, calm, confident, deliberate, slightly distinctive, and must never look like a generic SaaS or AI template. Derive a distinctive visual motif from the product (a card handed from one phone to another, a scan "moment") and apply it consistently.
- Typography: expressive editorial serif for names and key moments (Fraunces-like, variable) + restrained modern UI sans (not Inter; e.g. Instrument Sans or Geist, whichever exists in @fontsource). Max two UI families. Dramatic but intentional scale contrast, small precise utility type, tight display tracking, sensible line length. (The QR font library in STAGE 7 is separate and only applies to QR captions, exports and wallpapers.)
- Colour: warm white, soft grey, deep charcoal, deep navy, ONE disciplined accent, at most one small secondary. Light and dark themes via tokens. WCAG AA minimum. No neon, glow, cyan/purple gradients or gradient buttons. QR plates stay light with dark modules. (Bold social-style QR presets can be colourful; the app chrome stays restrained.)
- Layout: asymmetric editorial compositions, strong alignment anchors, generous whitespace that never pushes the QR or primary actions below the fold on a 360x640 screen, tight micro-spacing inside groups, consistent container widths, 4/8pt rhythm. Avoid centred-everything, identical cards everywhere, containers inside containers, the "big headline + tiny paragraph + two buttons" pattern, three-column icon cards, fake stats.
- Surfaces: flat, hairline borders, subtle elevation, moderate radius scale with sharper edges for editorial structure. No glassmorphism, no blur everywhere, no heavy shadows. Icons: Lucide only, one stroke weight, no emoji as UI, no brand glyphs (social rows use typographic labels).
- Motion: physical and quiet: opacity, small scale/translate, staggered type reveals, sheet transitions, press feedback, one satisfying moment when the QR appears or a style is applied. 150-350ms, natural easing, never blocks interaction, full prefers-reduced-motion support. Haptics on copy/save/apply/set-wallpaper through @capacitor/haptics.
- Native feel: bottom tab bar on owner screens (hidden on fullscreen QR and onboarding), Android back and iOS swipe-back, system sheets/share sheets, safe areas, edge-to-edge on Android SDK 36 (follow the current Capacitor 8 docs), 100dvh, inputs >= 16px, touch targets >= 44px, tablet/desktop as a considered two-pane composition.
- Apple's iOS 26 and Material 3 official kits are for correct sizes, safe areas, sheet behaviour and touch targets only. Do not adopt Liquid Glass or Material's default look.
- Accessibility: strong contrast, keyboard operation, visible focus, focus-trapped sheets with Escape, aria-live toasts, labelled controls, screen-reader names for every studio control, QR alternative text describing contents (never the raw payload), reduced motion.
- Decision filter for every element: does it improve usability, hierarchy or identity? If not, remove it.
Build design/tokens/tokens.json (colour, type scale, spacing, radius, elevation, motion, z-index, breakpoints; light and dark modes; Tokens Studio / W3C design-token compatible) and generate src/web/styles/tokens.css from it with a script, so design and code share one source. STAGE 6 - DATA, STORAGE AND CORE LOGIC
Storage layer: a `StorageAdapter` interface (getCard, saveCard, getPhoto, savePhoto, deletePhoto, getStyle/saveStyle, getSettings/saveSettings, clearAll) with two implementations chosen at runtime by Capacitor.isNativePlatform():
- Native: card JSON, style and settings in @capacitor/preferences; photo and imported assets as files in @capacitor/filesystem Directory.Data.
- Web: IndexedDB via idb-keyval; call navigator.storage.persist() on first save and show the result in Settings.
Rules: every record carries schemaVersion with a migration chain; debounced writes (400ms) flushed on blur/visibilitychange/pagehide; keep a `.bak` of the last good card and fall back to it if parsing/validation fails; a corrupted store never crashes the app (recovery screen: restore from backup file or start fresh); drafts autosave while editing and offer restore. Android: android:allowBackup="false" plus dataExtractionRules/fullBackupContent excluding everything, so Auto Backup never copies the card to a Google account.
Backup: Settings -> Export backup writes `<slug>-backup-YYYYMMDD.json` (card + style + settings + photo and custom images as base64, with schemaVersion) via native Share or a web download; Import validates with zod and replaces data after a confirmation sheet; "Erase all data" wipes storage and returns to onboarding.

Card model (zod, shared limits): id (uuid), firstName (required, 60), lastName (60), jobTitle (80), company (80), phone (E.164), email (254), website (normalized https URL), location (free text, 100), linkedin (canonical URL), instagram (handle), xHandle (handle), whatsapp (E.164), photoPresent, qrInclude (per-field booleans), createdAt, updatedAt, qrFingerprint. Normalizers: phone via libphonenumber-js with a default region constant "IN"; website http/https only (reject javascript:, data:), https-normalized, hostname with a dot; LinkedIn accepts URL, "in/handle" or bare handle, host must be linkedin.com, store canonical URL; Instagram ^[A-Za-z0-9._]{1,30}$ -> instagram.com/{handle}; X ^[A-Za-z0-9_]{1,15}$ -> x.com/{handle}; WhatsApp -> wa.me/{digits}. Trim strings, empty -> null, reject control characters. Social URLs are built from validated handles, never stored as arbitrary URLs.
Photo (fully on device): <input type="file" accept="image/*"> without `capture` (no camera permission); decode with createImageBitmap({imageOrientation:'from-image'}), centre-crop square, draw to canvas and export JPEG q0.82 at 512px (and 256px for the .vcf); re-encoding through canvas strips EXIF/GPS. Reject non-images, >12 MB, >8000px sides. The photo is never put in the QR.

QR payload (static vCard, deliberately small): compact vCard 3.0: BEGIN, VERSION:3.0, N, FN, ORG, TITLE, TEL;TYPE=CELL, EMAIL, one plain URL line per included link, END. No PRODID/REV/UID/PHOTO/item-group labels (saves bytes). CRLF, UTF-8, escape \ ; , and newlines. Location (if included) as ADR;TYPE=WORK:;;;<location>;;;. Per-field "Include in QR" toggles; default ON: name, title, company, phone, email, website; default OFF: location, LinkedIn, Instagram, X, WhatsApp. A live size meter shows bytes and QR version: green <= 250 bytes, amber 251-450, red > 450 with a hint to remove fields; hard cap 700 bytes. Byte mode, version auto. Error correction: M by default for plain QRs; Q selectable; H automatically when a centre element is used and for print exports. Always keep a quiet zone of >= 4 modules, always dark modules on a light plate (never inverted), PNG exports >= 1200px, SVG on screen. Static-QR honesty: when a change alters the payload (compare to qrFingerprint) show a calm banner after saving: "Your QR changed. Anything printed or saved earlier still shows the old details." with a "Got it" action. State this limitation in the README. Recipient experience: stock iPhone and Android cameras / Google Lens offer to add the contact straight from a vCard QR; document that this must be verified on real devices.

.vcf file export (richer): vCard 3.0, CRLF, UTF-8, fold lines at 75 OCTETS (never split a multibyte character), N, FN, ORG, TITLE, TEL;TYPE=CELL,VOICE, EMAIL;TYPE=INTERNET,WORK, URL;TYPE=WORK, ADR;TYPE=WORK:;;;<location>;;;, social links as itemN.URL + itemN.X-ABLabel (LinkedIn/Instagram/X/WhatsApp, numbered sequentially for existing ones only), PHOTO;ENCODING=b;TYPE=JPEG (256px base64, folded), UID urn:uuid:<card id>, PRODID, REV. Do not use X-SOCIALPROFILE. Filename ASCII-safe First-Last.vcf; MIME text/vcard; charset=utf-8. One vCard module with two modes (compact for QR, full for file) sharing the escaping/folding core. Delivery: native Share (Filesystem Cache + Share files), Web Share with file when canShare, else download.

STAGE 10 - PRIVACY ENFORCEMENT AND SECURITY
- CSP via <meta http-equiv> in index.html and a public/_headers file: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'none' (for the PWA build, scope to 'self' only if the service worker needs it, and document why); form-action 'none'; base-uri 'self'; object-src 'none'; frame-ancestors 'none' (header).
- `npm run check:privacy`: fails on fetch(, XMLHttpRequest, WebSocket, sendBeacon, EventSource or any http(s):// URL in app code (documentation strings and the reference list excepted) and on analytics SDKs in package.json.
- Playwright test records all requests across the full flow and asserts only same-origin static asset requests occur and none after load.
- Never use dangerouslySetInnerHTML; escape everything that reaches vCards and canvas text; treat imported backup files as hostile (zod validation, size limits).
- PWA: vite-plugin-pwa precaches the app shell, bundled fonts needed for defaults and icons; "Ready to work offline" toast; prompt-style update flow. Web manifest and icons so it is installable.
- docs/PRIVACY.md: the privacy policy in plain language (what is stored, where, that nothing is transmitted, what happens when the user shares, how to erase). Mirror it in the in-app Privacy screen. Make no claim you did not verify.

STAGE 14 - POLISH BACKLOG AND SCHEDULED FOLLOW-UPS (do this last, then finish the run)
The first run delivers the complete product. Small details that are not blockers get handled by recurring scheduled jobs afterwards, so you don't have to stall or over-polish now.
1. Create docs/BACKLOG.md: a prioritised list (maybe 25-40 items) of small improvements you noticed but did not do, each with an id, a one-line description, an estimated size (S/M) and acceptance criteria. Examples: micro-copy review, spacing and alignment audit per screen, preset tuning against scan-check results, extra tests, translation review notes, screenshot refresh, accessibility spot-checks, empty-state illustrations (kept within the design language), README polish, bundle-size trimming, dependency freshness report.
2. Create scripts/verify-all (the same checks as `npm run verify:all`) and scripts/polish-run.sh, which: takes a lock (skip if another run is active), checks out or creates a branch auto/polish-YYYYMMDD from main, picks the top 3 open S/M items from docs/BACKLOG.md, implements them, runs verify:all, commits with a conventional message that cites the item ids, marks them done in the backlog, appends to CHANGELOG.md, and writes a log to logs/cron/ (gitignored). If verify:all fails, revert that item's changes, mark the item "blocked" with the reason, and continue with the next.
3. Set up recurring scheduled jobs using whatever scheduling facility your environment gives you (an agent scheduler, a cron tool, or similar). Suggested schedule: a daily polish pass (polish-run), a nightly smoke run (verify:all, reporting only), and a weekly dependency report (`npm outdated` and `npm audit` written to docs/DEPENDENCY_REPORT.md, no automatic major upgrades). If your environment has no scheduler, do NOT edit the system crontab. Instead write docs/AUTOMATION.md with the exact cron/launchd/GitHub Actions lines the owner can install, make the scripts runnable, and say so in the final report. (A GitHub Actions scheduled workflow may run the nightly smoke test and the dependency report, but must not run AI-driven edits.)
4. Guardrails for every scheduled job: work only on branches named auto/*, never push to main, never force-push, never rewrite history, never change secrets or signing files, never add network calls or analytics, never do major-version upgrades, never delete user-facing features, honour the privacy model, timeouts of 30 minutes per run, one run at a time, and stop and mark the job done when the backlog has no open items. Each run appends a short entry to docs/AUTOMATION.md (what ran, what changed, what failed).
5. Document the whole mechanism in docs/AUTOMATION.md: what each job does, schedule, how to pause or remove it, and how to review and merge the auto/* branches.
